# Leaderboard board contracts

This document defines the canonical contract for every seasonal leaderboard board. The five boards share one authoritative entry table (`public.leaderboard_entries`) and are materialized by the `snapshot_leaderboard_season` RPC into immutable `public.leaderboard_season_snapshots` rows. Browser reads flow through the privacy-definer `read_leaderboard` RPC, which applies the same ordering.

The contract is derived from gameplay semantics already implemented in `server/mission.ts` (`calculateResult`) and `shared/protocol.ts` (`MissionResult`). No board invents client-submitted data; every value is produced by the authoritative mission server.

## Shared entry requirements

Every verified entry must satisfy all of the following before it is eligible for any board:

| Field | Constraint | Source |
| --- | --- | --- |
| `verified` | `true` | Set by `record_verified_leaderboard_entry` after identity and bounds checks |
| `season_id` | References an existing `leaderboard_seasons.id` | Captured at mission launch; immutable for the run's lifetime |
| `mission_started_at` | Within the season's `[starts_at, closed_at]` window (or `[starts_at, ends_at]` for open/closing seasons) | Server-authoritative clock at run start |
| `mission_version` | Valid semver or `legacy` | From the mission definition loaded by the room |
| `mission_content_hash` | `fnv1a32:<8 hex>` or `legacy` | Content hash of the loaded mission package |
| `score` | 0–10,000 | Weighted mastery score from `calculateResult` |
| `grade` | `S` \| `A` \| `B` \| `C` | Thresholded from `score` using mission-defined thresholds |
| `mission_seconds` | 1–86,400 | Wall-clock run duration, rounded |
| `delivered` | 0–1,000,000 | Community coin or captive value delivered to the village |
| `rescues` | 0–1,000 | Count of `player_freed` events during the run |
| `damage_taken` | 0–1,000 | Accumulated damage across the band |
| `precision` | 0–100 | `shotsHit / shotsFired * 100` (100 if no shots fired) |
| `generosity` | 0–100 | `(totalTransferred / delivered) * 200`, clamped |
| `clean_escape` | `true` iff `damageTaken === 0` AND no `player_captured` event | Derived server-side at run end |
| `character_id` | `robin` \| `marian` \| `little-john` \| `much` | Selected at room join |
| `party_size` | 1–4 | Number of connected players at mission start |
| `band_id` | Nullable; references `merry_bands` when the run is a band mission | Captured at mission launch |

### Idempotency and replay

- `verification_id` is a deterministic UUIDv5-like digest of `(mission_id, player_id)` generated by `verificationId()` in `server/leaderboard-store.ts`. The same run always produces the same UUID.
- `record_verified_leaderboard_entry` uses `ON CONFLICT (verification_id)` to make exact replays idempotent: the same inputs return the same entry ID.
- A conflicting payload with the same `verification_id` raises `VERIFICATION_CONFLICT`.
- After a season is `finalized`, new entries raise `SEASON_FINALIZED`; exact replays of already-recorded entries still return their ID.

### Quarantine and corrections

An entry is quarantined (stored in `leaderboard_quarantine`, not promoted) when any of these server-observable conditions hold:

- `score > 10000` (`score:above-maximum`)
- `mission_seconds < 60` (`time:below-minimum`)
- `precision < 0 OR precision > 100` (`precision:out-of-range`)
- `player_name` fails the alias regex (`name:invalid`)

A quarantined run can be promoted to verified only through operator review (`review_leaderboard_quarantine` with `decision: "approved"`), which inserts it with `suspicious = true`. A rejected run never enters any board. The review decision is terminal: the opposite decision raises `REVIEW_DECISION_CONFLICT`.

A corrected result is not an in-place edit. The original entry is superseded by a new `verification_id` from a new authoritative run. Historical snapshots are append-only and never mutated.

## Board definitions

### 1. Master Outlaws

**Recognition:** Highest validated mission mastery score.

**Scope:** All verified entries for the season.

**Ordering (deterministic):**
1. `score` DESC (higher mastery first)
2. `mission_seconds` ASC (faster completion breaks ties)
3. `id` ASC (stable insertion order)

**Partial index:** `leaderboard_entries_ranking_idx` on `(season_id, verified desc, score desc, mission_seconds asc, created_at asc)`.

### 2. People's Champions

**Recognition:** Most wealth successfully redistributed to communities.

**Scope:** All verified entries for the season.

**Ordering:**
1. `delivered` DESC (more community coin / captive value first)
2. `score` DESC (mastery breaks ties)
3. `id` ASC

**Partial index:** `leaderboard_entries_champion_v2_idx` on `(season_id, delivered desc, score desc, id)`.

### 3. Clean Escapes

**Recognition:** Highest-value missions completed without damage or capture.

**Scope:** Verified entries where `clean_escape = true` (derived: `damageTaken === 0` AND no `player_captured` event occurred).

**Ordering:**
1. `delivered` DESC (highest value first)
2. `score` DESC (mastery breaks ties)
3. `mission_seconds` ASC (faster breaks ties)
4. `id` ASC

**Partial index:** `leaderboard_entries_clean_v2_idx` on `(season_id, delivered desc, score desc, mission_seconds asc, id) WHERE verified = true AND clean_escape = true`.

### 4. Rescuers

**Recognition:** Most seized teammates freed and rescue missions completed.

**Scope:** All verified entries for the season.

**Ordering:**
1. `rescues` DESC (more rescues first)
2. `score` DESC (mastery breaks ties)
3. `id` ASC

**Partial index:** `leaderboard_entries_rescuer_idx` on `(season_id, rescues desc, score desc) WHERE verified = true`.

### 5. Swift Arrows

**Recognition:** Fastest validated heist completion, ranked independently per mission and party size.

**Scope:** All verified entries for the season. The board is partitioned by `(mission_slug, party_size)`.

**Ordering (within each partition):**
1. `mission_seconds` ASC (faster first)
2. `score` DESC (mastery breaks ties)
3. `precision` DESC (accuracy breaks ties)
4. `id` ASC

**Partial index:** `leaderboard_entries_swift_v2_idx` on `(season_id, mission_slug, party_size, mission_seconds asc, score desc, precision desc, id) WHERE verified = true`.

The snapshot RPC limits each partition to the top 50 entries (`group_rank <= 50`) and preserves the full row payload so consumers can render per-mission, per-party-size boards without re-querying.

## Filter dimensions

`read_leaderboard` exposes the following filters. Every filter is applied server-side in the security-definer RPC; callers cannot supply arbitrary values outside their scope.

| Filter | Parameter | Constraint |
| --- | --- | --- |
| Board kind | `p_kind` | `master-outlaws` \| `peoples-champions` \| `clean-escapes` \| `rescuers` \| `swift-arrows` |
| Season | `p_season_slug` | Must reference a public season |
| Character | `p_character_id` | `robin` \| `marian` \| `little-john` \| `much` or NULL |
| Party size | `p_party_size` | 1–4 or NULL |
| Mission | `p_mission_slug` | Slug regex or NULL |
| Band scope | `p_band_id` | Caller must be an active member of that band |
| Friend scope | `p_player_ids` | Each ID must be the caller or an accepted friend; anonymous callers receive `[]` |
| Exclusion | `p_excluded_player_ids` | Bilateral block suppression is applied automatically regardless of this parameter |

## Season lifecycle and rollover invariants

### States

`leaderboard_seasons.lifecycle_state ∈ {open, closing, finalized}`

| State | Accepts new entries | Accepts reviews | Snapshots writable |
| --- | --- | --- | --- |
| `open` | Yes | Yes | No |
| `closing` | Only if `mission_started_at <= closed_at` | Yes | No |
| `finalized` | No (exact replay only) | No | No (append-only) |

### Invariants

1. **Mission start locks the season.** The season is captured at mission launch. A later pause, archive, or successor season cannot retroactively move that run to a different season.
2. **Closing window is bounded.** `finalize_after >= closed_at`. The drain window is at least 30 minutes (set by `sync_leaderboard_season_from_campaign` on archive). This window lets in-flight runs finish and be recorded before finalization.
3. **No pending reviews at finalization.** `finalize_due_leaderboard_seasons` skips any season that has a quarantine row with `status = 'pending'` for that season.
4. **Five snapshots per finalized season.** `snapshot_leaderboard_season` writes exactly five rows (one per board) and raises `INCOMPLETE_LEADERBOARD_SNAPSHOT` if any board is missing. It marks the season `finalized` only after all five succeed.
5. **Snapshots are immutable.** The `leaderboard_snapshots_append_only` trigger raises `IMMUTABLE_LEADERBOARD_RECORD` on any UPDATE or DELETE. Campaign events (`sherwood_campaign_events`) have the same guard.
6. **Finalized seasons are append-only.** The `leaderboard_entries_finalized_guard` trigger raises `SEASON_FINALIZED` on INSERT. Exact replays (same `verification_id`) return the existing ID without error.
7. **Browser roles never see raw entries or snapshots.** All reads go through `read_leaderboard`, which strips `player_id`, `verification_id`, `score_breakdown`, and `suspicious`. Direct table SELECT is revoked from `anon`, `authenticated`, and `public` roles.
8. **Recognition persists across rollover.** The season snapshot carries forward accumulated `recognition` (generosity, rescues, cleanEscapes, tactical). Starting a successor season preserves the previous recognition totals; it does not reset them.

### Finalization flow

```
archive campaign
  -> record_sherwood_campaign_transition sets lifecycle_state = 'closing',
     closed_at = now, finalize_after = now + 30 min
-> finalize_after elapses AND no pending quarantines
     -> finalize_due_leaderboard_seasons() runs snapshot_leaderboard_season()
     -> five snapshot rows written
     -> lifecycle_state = 'finalized', finalized_at = now
-> subsequent new entry attempts raise SEASON_FINALIZED
-> exact replays return the original entry ID
```
